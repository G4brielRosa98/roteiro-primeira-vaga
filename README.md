##   Etapa 5.1 — Mini-projetos no GitHub (da semana 1 à 12\)

Publique o primeiro já na primeira semana e vá subindo um por vez. Recrutador olha o GitHub por menos de um minuto, então o que conta é: tema próprio (nada de "lista de tarefas" copiada de tutorial), README claro e sinais de capricho.

Todos usam a sua vantagem: você entende de rede e fibra, e quase nenhum outro iniciante entende.

### 5.1 Calculadora de sub-redes — JavaScript / Node.js (2 a 3 dias)

- **O que faz:** recebe um endereço como `192.168.10.0/26` e mostra rede, broadcast, máscara, primeiro e último host e quantidade de hosts.  
- **Como fazer:** programa de linha de comando em Node.js, sem bibliotecas prontas de IP. A graça é você implementar a conta.  
- **O que demonstra:** lógica, manipulação de bits e strings, e domínio de endereçamento IP.  
- **Para chamar atenção:** testes automatizados (o Node já traz um executor de testes) e uma tabela de exemplos no README.

### 5.2 Calculadora de orçamento de potência óptica — Python (3 a 4 dias)

- **O que faz:** recebe distância do enlace, número de emendas, conectores e splitters (1:8, 1:16, 1:32...) e calcula a atenuação total, a potência que chega na ONU e se o enlace passa ou não.  
- **Como fazer:** linha de comando em Python, com os valores de perda por km, por emenda, por conector e por splitter em um arquivo de configuração, para ajustar conforme o fabricante.  
- **O que demonstra:** Python, funções bem organizadas, leitura de arquivo e conhecimento real de FTTH.  
- **Para chamar atenção:** é o projeto mais raro da lista. No README, explique o cálculo com um exemplo de enlace real.

### 5.3 API de monitoramento de equipamentos — Node.js (1 a 2 semanas) ⭐ projeto principal

- **O que faz:** API REST para cadastrar equipamentos (nome, IP, local), testar periodicamente quem está online e guardar o histórico de quedas.  
- **Como fazer:** Node.js com Express ou Fastify, banco SQLite ou PostgreSQL, rotas de CRUD, uma tarefa agendada que faz a checagem e uma rota de resumo ("online agora", "quedas nas últimas 24 h").  
- **O que demonstra:** o que uma vaga de back-end júnior pede: API, banco de dados, SQL, organização em camadas e tratamento de erros.  
- **Para chamar atenção:** documentação das rotas com exemplos de requisição e resposta, arquivo `.env.example`, testes das rotas principais e, se der, TypeScript.

### 5.4 Painel de status — HTML, CSS e JavaScript (3 a 5 dias)

- **O que faz:** página que consome a API do 5.3 e mostra os equipamentos em verde ou vermelho, com atualização automática.  
- **Como fazer:** JavaScript puro com `fetch`, sem framework.  
- **O que demonstra:** que você sabe ligar front-end e back-end.  
- **Para chamar atenção:** **publique online** (GitHub Pages para o painel e uma hospedagem gratuita para a API) e coloque o link no topo do README. Projeto que abre com um clique vale por dez que exigem instalar.

### 5.5 Bot de alertas no Telegram — Python (3 a 4 dias)

- **O que faz:** avisa em um grupo do Telegram quando um equipamento cai ou volta, e responde a comandos como `/status` consultando a API do 5.3.  
- **O que demonstra:** integração entre sistemas e automação, que é o dia a dia de qualquer time de operação.  
- **Para chamar atenção:** um GIF curto no README mostrando o alerta chegando no celular. É o tipo de coisa que um dono de provedor entende na hora.

### 5.6 Resumo de logs com IA — Python ou Node.js (3 a 5 dias, opcional)

- **O que faz:** lê um arquivo de log de equipamento e usa a API do Claude para gerar um resumo em português: o que aconteceu, quando e o que investigar.  
- **Como fazer:** script que lê o arquivo, monta o prompt e chama a API. A chave fica em variável de ambiente, **nunca** no repositório.  
- **Observação:** a API do Claude é cobrada por uso, separada da assinatura do chat. Para estudo o gasto é pequeno, mas defina um limite de crédito.

Seis aulas práticas, de 30 a 40 minutos cada. Dá para fazer em uma tarde ou em três noites. Ao final você terá o perfil pronto, o repositório do roteiro no ar e o fluxo que vai usar em todos os mini-projetos.

## Aula 1 — O que é o quê, e instalação

**Conceitos**

- **Git:** programa instalado na sua máquina que guarda o histórico de versões de uma pasta.  
- **GitHub:** site onde você publica essas pastas (repositórios) para outras pessoas verem.  
- **Repositório:** uma pasta de projeto controlada pelo Git.  
- **Commit:** uma "foto" do projeto em um momento, com uma mensagem explicando o que mudou.

**Prática**

1. Crie a conta em github.com com um nome de usuário profissional.  
2. Instale o Git (git-scm.com) e o VS Code (code.visualstudio.com).  
3. Abra o terminal e configure seu nome e e-mail (use o mesmo e-mail da conta do GitHub):

```sh
git --version
git config --global user.name "Seu Nome"
git config --global user.email "seu-email@exemplo.com"
git config --global init.defaultBranch main
```

**Pronto quando:** `git --version` mostra um número de versão e `git config --list` mostra seu nome e e-mail.

## Aula 2 — Primeiro repositório local

**Conceitos:** o ciclo de três passos que você vai repetir para sempre: **editar → `add` → `commit`**.

**Prática**

```sh
mkdir roteiro-primeira-vaga
cd roteiro-primeira-vaga
git init
```

Crie um arquivo `README.md` com um título e uma frase. Depois:

```sh
git status                 # mostra o que mudou
git add README.md          # escolhe o que entra na próxima "foto"
git commit -m "Cria README inicial"
git log --oneline          # mostra o histórico
```

Edite o README, adicione uma linha e repita `status`, `add`, `commit`. Antes de adicionar, rode `git diff` para ver exatamente o que mudou.

**Boas mensagens de commit:** curtas, no presente, dizendo o que o commit faz. "Adiciona cálculo de broadcast" é bom. "ajustes" e "agora vai" não são.

**Pronto quando:** `git log --oneline` mostra pelo menos três commits com mensagens claras.

## Aula 3 — Publicando no GitHub

**Conceitos**

- **Remoto (`origin`):** a cópia do repositório que fica no GitHub.  
- **`push`:** envia seus commits para o GitHub. **`pull`:** traz o que está lá para a sua máquina.

**Prática**

1. No GitHub, clique em **New repository**, dê o nome `roteiro-primeira-vaga`, deixe público e **não** marque nenhuma opção de criar README.  
2. Na primeira vez, o Git vai pedir login. O caminho mais simples é instalar o GitHub CLI (cli.github.com) e rodar `gh auth login`, seguindo as instruções na tela.  
3. Conecte e envie:

```sh
git remote add origin https://github.com/SEU-USUARIO/roteiro-primeira-vaga.git
git push -u origin main
```

4. Atualize a página do repositório no navegador: seus arquivos e commits estão lá.  
5. Faça mais uma alteração, `add`, `commit` e agora só `git push`.

Para baixar um repositório que já existe no GitHub para a sua máquina, use `git clone URL-DO-REPOSITORIO`.

**Pronto quando:** o repositório abre no navegador, com o README aparecendo na página inicial.

## Aula 4 — README, Markdown e perfil

**Conceitos:** o README é a vitrine. É escrito em Markdown, a mesma linguagem deste arquivo.

**Markdown essencial**

```
# Título
## Subtítulo
**negrito** e `código`
- item de lista
- [ ] tarefa pendente
- [x] tarefa concluída
[texto do link](https://exemplo.com)

```

**Prática**

1. Coloque o roteiro completo como README do repositório `roteiro-primeira-vaga` e marque com `[x]` o que já concluiu. Commit e push.  
2. Crie um repositório público com **exatamente o mesmo nome do seu usuário**. O README dele aparece no topo do seu perfil. Escreva: quem você é, o que está estudando, seus projetos e como falar com você.  
3. No seu perfil, preencha foto, bio, cidade e link do LinkedIn.

**Modelo de README para projetos**

```
# Nome do projeto

Uma frase dizendo o que ele faz.

## Como rodar
1. `git clone ...`
2. `npm install`
3. `npm start`

## O que aprendi
- ...

## Próximos passos
- ...
```

**Pronto quando:** seu perfil mostra o README de apresentação e o repositório do roteiro tem caixinhas marcadas.

## Aula 5 — .gitignore, segredos e como desfazer

**Conceitos**

- **`.gitignore`:** arquivo que lista o que o Git **não** deve guardar.  
- Nunca vão para o GitHub: senhas, tokens, chaves de API, arquivo `.env`, a pasta `node_modules` e dados reais de clientes.

**Prática**

Crie um arquivo `.gitignore` na raiz do projeto:

```
node_modules/
.env
__pycache__/
*.log
```

Para chaves e senhas, use um arquivo `.env` (ignorado) e publique um `.env.example` só com os nomes das variáveis, sem os valores.

**Como desfazer**

```sh
git restore arquivo.js            # descarta alterações ainda não commitadas
git restore --staged arquivo.js   # tira do "add", mantendo a alteração
git commit --amend -m "Nova mensagem"   # corrige a mensagem do último commit (antes do push)
git revert HASH-DO-COMMIT         # cria um novo commit que desfaz um commit antigo
```

**Se uma senha ou chave for parar no GitHub:** apagar o arquivo não resolve, porque ela continua no histórico. Troque a senha ou revogue a chave imediatamente.

**Pronto quando:** você criou um `.env` de teste, confirmou com `git status` que ele não aparece, e desfez uma alteração com `git restore`.

## Aula 6 — Branches e pull request

**Conceitos**

- **Branch:** uma linha paralela de trabalho. Você mexe nela sem quebrar a `main`.  
- **Pull request (PR):** o pedido para juntar uma branch à `main`. É como as equipes trabalham e revisam código nas empresas, então aparece em entrevista.

**Prática**

```sh
git switch -c melhora-readme      # cria a branch e muda para ela
# edite o README
git add README.md
git commit -m "Adiciona seção de próximos passos"
git push -u origin melhora-readme
```

No GitHub, vai aparecer o botão **Compare & pull request**. Abra o PR, escreva o que mudou, confira a aba de arquivos alterados e clique em **Merge**. Depois, na sua máquina:

```sh
git switch main
git pull
git branch -d melhora-readme
```

**Pronto quando:** o repositório mostra um pull request fechado (merged) e sua `main` local está atualizada.
